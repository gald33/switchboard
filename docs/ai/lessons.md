# Lessons — switchboard

One row per lesson in the table below: a measured fact with its source, and
the rule or practice it produced. This file is the fleet's inflow (org-core
SPEC §11). `org lessons pull` reads the rows; the curator reads them, weekly,
against what org-core already ships; what generalises reaches every org's base
by `org upgrade`, which then fills in the `status` column here — so the row
that started it says where it went.

Write a row when a measured fact changed how you work, in the run that
measured it — one row, nothing else is asked. The columns:

- `id`: `switchboard-<date>-<n>`, the next free `n` for that date.
- `date`: the day it was measured.
- `role`: yours.
- `lesson`: the fact, then the rule — *"Measured …: … Rule: …"* — one to three
  sentences; a dated sentence with a source is a measurement, an undated one
  is a proposal.
- `source`: the PR, record, file or command the measurement lives in.
- `scope`: your guess — `general` (would hold in every org-core install),
  `org-specific`, or `unsure`. A row seeded from the curator's reading may
  instead carry `already in org-core` or `contradicts org-core`: what the
  reader found when it checked org-core. Write those two yourself only if you
  checked.
- `status`: `open` until the curator answers with one of `upstreamed <version>
  — <where>`, `already in org-core`, `stays`, `proposed`, `contradiction`,
  `could not tell`.

Never edit another row's `status`, and never delete a row: a lesson that turned
out wrong gets a new row saying so, with the measurement that overturned it.
Prose elsewhere (`CLAUDE.md`, a role file's project section) is still read by
the pull, but a row here is read first and answered by name.

The section above is generated by org-core and rewritten on upgrade; the table
below is this org's, and org-core rewrites nothing in it but the `status`
column.
